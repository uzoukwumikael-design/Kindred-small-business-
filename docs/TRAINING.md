# Training the helpers with real data

Kindling has a small model of its own, and a data layer that lets it learn from real examples that people choose to share.
This page explains what exists, how to retrain it, and where the honest limits are.

## What is trained

**The need model** reads a customer message and predicts two things:

1. which of the shop's facts it needs (hours, location, payment, delivery, prices, booking, returns, contact), and
2. the kind of job it is (a plain reply, a booking change, or a quote).

It is a small linear model (word, word-pair and character features, one logistic regression per fact, one softmax for the job
type) written in TypeScript. It trains in seconds on a laptop, needs no GPU, and its whole file is under 500 KB.

It is used in three places:

- the grey hint under the note box ("this message looks like it asks about prices, you have not saved that fact"),
- the offline template drafter, to pick the right checked fact to answer with,
- the front-page quick draft, to choose between a reply, a booking confirmation and a quote.

It does not write drafts. The AI service does that. Writing quality is checked with `npm run eval` (see the README).

## Where the data comes from

1. **Seed data** (`data/seed/needs.jsonl`) is generated by `npm run seed` from hand-written templates in English and common Pidgin,
   with typos and chatty openings. It is synthetic. Whole template families are held out for validation.
2. **A hand-written test set** (`data/seed/hard-set.jsonl`, 64 messages) is never trained on. It is what the report leads with.
   I wrote it, and I also wrote the templates, so it is not fully independent. A set written by a shop owner would be better.
3. **Real examples** come from the data layer, and only from people who switched it on.

## The data layer

People switch it on in their account (off by default, unticked). Then, under any finished draft, they can press "Share this example".
They see a preview of exactly what will be sent and can edit it. Before that, card numbers, ID numbers, emails, phone numbers,
passwords and names are masked in their browser.

What is stored per example (`kindling_training_examples`): the masked customer message, the first draft, the final reply, the channel,
the language, which fact types the reply used, how many brackets the draft had, how many double-check warnings, how much the person
changed the draft, and whether the draft came from live AI or the template. No name, email or shop details are in the row, but the
row is tied to the account so it can be deleted.

The database enforces the rules (`supabase/schema.sql`, tested on real Postgres):

- a row can be added only by someone who has consented, only for themselves, up to 200 rows;
- people can read and delete their own rows, never edit them;
- switching consent off deletes all their rows, by a database trigger, so it cannot be skipped;
- deleting the account deletes the rows.

Names are masked by a pattern guess (greetings, "it's Maria", "Maria here"), which will miss some. The preview exists for that reason.

## Retraining

    # 1. export the shared examples (needs the Supabase service role key, keep it private)
    SUPABASE_SERVICE_ROLE_KEY=... VITE_SUPABASE_URL=... npm run export-training

    # 2. retrain the need model on seed plus real data, and compare it with the keyword rules
    npm run train -- --extra data/exports/needs.jsonl --must-beat-baseline

The export keeps only rows from people whose consent is still on, masks again and drops any row where something private-looking is left,
and replaces user ids with a salted one-way cohort code. `npm run train` writes `src/lib/kindling/needs/need-model.json` and
`docs/MODEL_REPORT.md`. Commit both and deploy. With `--must-beat-baseline` it exits with an error if the new model is not better than
the old keyword rules on the hand-written test set, so a bad retrain does not ship.

The need labels from real data are weak: they come from which fact types the final reply used plus what the keyword rules see in the
message. That is good enough to start and should be corrected by hand as the data grows. Add real-world test messages to
`data/seed/hard-set.jsonl` as you find mistakes.

## Fine-tuning a language model (not done, and not recommended yet)

`npm run export-training` also writes `finetune-train.jsonl` and `finetune-val.jsonl` in chat format (system, user, assistant). That is
the format most fine-tuning services accept. I have not run any fine-tuning and cannot from here. Before you try:

- you need at least a few hundred good examples per language, and the exporter warns when there are fewer than 300;
- check the provider's terms for what they do with training data, because that is a new place customer text would go;
- fine-tune only if `npm run eval` shows the base model is failing in ways examples can fix, and run `npm run eval` again afterwards to see
  whether the tuned model really is better. A fine-tuned model that sounds fluent can still invent a price.

Pidgin, Yoruba, Igbo and Hausa are where real examples help most, because general models are weakest there. The seed data has
no Yoruba, Igbo or Hausa on purpose: I am not confident enough in those languages to write training data, and a model trained on wrong
data is worse than none. Those need examples labelled by native speakers.

## Consent and law

Training on customer content needs a clear reason and consent. The privacy page and `docs/COMPLIANCE.md` describe this feature. Have your
lawyer or data protection adviser confirm it, in particular: the consent wording, how long you keep the data, who can run the export,
and where the exported files are stored. Do not commit `data/exports/` (it is ignored in `.gitignore`).
